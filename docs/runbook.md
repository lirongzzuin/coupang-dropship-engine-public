# 운영 런북 (runbook.md)

## 1. 평소 운영 — 목표 하루 5분

시스템이 자동으로 하는 일(주기는 설정 > 고급 > `schedule`에서 변경):

| 작업 | 주기 | 내용 |
|---|---|---|
| 주문 수집·처리 | 5분 | 새 주문 감지 → 재고·가격 재확인 → 쿠팡 상품준비중 → **API 공급처는 자동 발주** / 아니면 구매 작업 알림, 취소·반품 감지 |
| 송장 회수·배송 추적 | 10분 | 공급처 송장 조회 → 쿠팡 업로드 → 배송중·배송완료 반영, 지연 경고 |
| 가격·재고 동기화 | 60분 | 품절·옵션 삭제·오픈마켓 판매 금지·재고 3개 미만·공급처에서 삭제 시 판매중지, 회복 시 재개, 공급가 상승 시 판매가 인상(하한 엄수), 손실·최저판매준수가 미달이면 중지. 판매 부진·장기 판매불가 상품 종료 |
| 주문 가능 점검·쿠팡 대조 | 60분(상품별 24시간) | 오너클랜 주문 시뮬레이션(주문 생성 없음)으로 실제 발주 가능 여부·실주문 금액 확인, 쿠팡 실제 판매상태와 대조 |
| 상품 승인 상태 | 30분 | 쿠팡 심사 결과 반영(승인 → 판매중, 반려 → 알림) |
| 상품 선정 | 24시간 | 시드 키워드 + 잘 팔리는 상품의 키워드로 후보 선정, **auto 모드면 조건 충족 상위 N개 자동 등록**. 판매 부진 상품은 1회 인하 후 종료 |
| 고객문의 | 30분 | 배송 문의는 템플릿 자동 답변, 불만·환불은 초안 + 알림 |
| 정산 대사 | 24시간 | 쿠팡 매출내역 → 주문별 확정 이익, 보관기간 지난 개인정보 파기 |
| 일일 리포트 | 매일 09시 | 텔레그램으로 어제 매출·이익·할 일·키 만료 D-day |
| 감시 | 10분 | 주문 수집이 30분 이상 멈추면 알림, 키 만료 D-14/7/3/1 알림 |

**사람이 하는 일**
- **매일(텔레그램 알림이 올 때만)**
  - 🛒 "구매할 주문이 있어요": API가 없는 공급처 상품입니다. 알림 링크 → [공급처 상품 페이지 열기] → 배송지 [복사] → 결제 → 주문번호 입력(1~2분). 공급처가 송장 API를 주지 않으면 송장도 입력(20초).
  - 🛒 "공급처 결제가 필요해요": 예치금이 부족하거나 결제가 승인 대기입니다. 공급처에서 결제한 뒤 [구매 완료]를 누릅니다.
  - 🚨 예외(품절·마진 역전·한도 초과·송장 지연·취소/반품 요청): 주문 화면의 안내대로 [강행] 또는 Wing에서 취소 처리 후 [취소됨으로 표시]합니다.
- **매주(10분)**
  - 공급처 예치금 충전, 카드 한도 확인
  - 쿠팡 Wing > 판매자 점수 확인(API로 조회할 수 없음)
  - (선택) 쿠팡 판매량 추정 CSV 업로드(작업 화면)
  - 후보 탭에서 이미지 직접 제작이 필요한 우수 후보를 승인할지 판단

## 3. 실운영 전환(`golive.sh`)
1. `bash ~/dropship/bin/golive.sh check` — 조회만으로 준비 상태 점검(텔레그램, 쿠팡 판매자 정보·API, 오너클랜 로그인·주문 권한, 이미지 공개 주소 접속, 보내는 사람, 후보)
2. 오너클랜 예치금 충전(처음 10~20만원). 자동 발주는 예치금에서 결제됨
3. `bash ~/dropship/bin/golive.sh` — 점검 → 쿠팡 등록 사전 점검(임시저장 후 삭제) → `yes` 입력 시 `.env` 백업 후 `DRY_RUN=false` + 모든 `LIVE_*=true` → 재시작
4. 되돌리기: `bash ~/dropship/bin/golive.sh off`(모의 실행). 급할 때는 관리 화면 **[긴급 정지]**
5. 첫 2주: 한도(설정 > 주문: 건당 10만원·일 50만원)를 유지하고 예외 건수·출고 지연·실제 이익 확인 후 조정

안전장치(스위치를 일부만 켜도 실제 주문이 사라지지 않음):
- 실제 쿠팡 상품의 주문인데 `LIVE_FULFILLMENT`/`LIVE_ORDERING`이 꺼져 있으면 **모의 처리하지 않고** "구매 필요"로 넘기고 텔레그램으로 할 일을 보냄
- 송장 자동 등록이 꺼져 있으면 "송장 직접 입력 필요"(Wing)로 알림
- 실등록(`LIVE_LISTING`)만 켜도 실제 쿠팡 상품의 가격·재고·판매중지는 실제로 반영(품절 주문·역마진 방지)
- 오너클랜 결제 대기 → 결제되면 자동 진행, 공급사 취소(품절) → 상품 중지 + 알림, 고객 취소 → 오너클랜 주문 자동 취소(요청)

## 3-0. 상품 감시·정리 — 공급처에서 주문할 수 없는 상품은 팔지 않는다

**1) 판매 가능 감시(가격·재고 동기화, 60분)** — 판매중·자동 중지 상품을 공급처에서 다시 조회
- **올린 옵션 고정**: 옵션 상품은 쿠팡에 올린 옵션(예: 빨강)만 본다. 그 옵션이 품절이면 다른 색으로 바꿔 보내지 않고 판매중지, 재입고되면 재개. 발주도 항상 그 옵션으로. 관리 화면 상품·주문에 "발주 옵션" 표시
- 판매중지 사유(텔레그램에 상품별 사유): `공급처 품절`(옵션 품절 포함) · `공급처 판매 불가`(단종·옵션 삭제·착불 전환·**오픈마켓 판매 금지**·공급처에서 삭제) · `공급처 재고 부족`(기본 3개 미만 — 다른 판매자 주문으로 곧 품절) · `마진 역전` · `최저판매준수가 미달`(가격을 올려 보고 가드로 못 맞출 때) · `공급처 확인 불가`(이 상품만 6회 연속 조회 실패, 공급처 전체 장애면 멈추지 않음)
- 위 사유는 공급처가 회복되면 **자동 재개**(안전장치 판매 중지 중엔 재개 안 함)

**2) 주문 가능 점검(60분마다, 상품별 24시간 간격, 1회 최대 20개)** — 오너클랜 `simulateCreateOrder`(주문을 만들지 않는 시뮬레이션)에 **우리 반품지 주소**로 1개 주문을 넣어 본다(고객 정보 사용 안 함)
- 공급처가 거부 → `주문 불가`로 판매중지. 동기화는 재개하지 않고, 다음 점검이 통과하면 재개
- 실주문 금액(상품+배송비) 기준 손실 → `주문 불가`(손실)로 중지. 이익은 남지만 예상보다 500원 넘게 비싸면 알림만
- 한 번에 3개 이상·절반 이상 거부되면 상품 문제가 아니라 연동 문제로 보고 **멈추지 않고** "연동 문제 의심" 알림
- 반품지 주소·연락처(설정 > 쿠팡)가 없으면 점검하지 않음. 연결 확인: `bash ~/dropship/bin/check.sh`의 "오너클랜 주문 가능 점검(시뮬레이션)"

**3) 쿠팡 판매상태 대조(60분)** — 쿠팡 옵션별 판매상태(inventories 조회)와 비교
- 우리가 멈춘 상품(일시중지·최근 7일 판매종료)인데 쿠팡에서 판매중 → 다시 판매중지(실패하면 "Wing에서 직접 중지" 알림)
- 우리는 판매중인데 쿠팡에서 모든 옵션이 판매중지 → `쿠팡에서 판매중지됨`(Wing·쿠팡 조치)으로 기록, **자동 재개 안 함**
- 사람이 멈춘 상품(관리자 중지·쿠팡에서 판매중지됨)을 Wing에서 다시 판매하면 그 결정을 따름(공급처 상태는 다음 동기화가 확인)
- 조회가 전부 실패하면 하루 한 번 "쿠팡 판매상태 조회 실패" 알림

**4) 정리(걸러내기)**
- **판매 부진**: 최근 14일 판매 0(취소 제외) → 하한가로 1회 인하 → 10일 더 0건이면 판매종료. 다시 팔리면 인하 이력 초기화
- **장기 판매불가**: 공급처 사유·주문 불가로 14일 넘게 멈춘 상품 → 판매종료(사람·안전장치·쿠팡 중지는 사람이 판단)
- **우선순위 교체**(선정 때): 운영 상품 수가 상한(30)이면, 등록 30일이 지났고 최근 30일 실제 월이익이 3만원 미만인 상품 중 가장 낮은 것을, 기대 월이익이 그 2배 이상(최소 1만원)인 새 후보로 교체. 1회 최대 2개. 새 상품 등록이 실패하면 기존 상품을 되살림. 선정 결과 알림에 "🔁 우선순위 교체" 표시
- 실제로 올렸다가 종료한 상품은 다시 후보로 올리지 않음(쿠팡 중복 등록 방지). 다시 팔려면 관리 화면 상품 > [판매재개]
- 매일 리포트: 일시중지 사유별 개수, 공급처 확인이 밀린 판매중 상품 수

설정: `monitor`(minSourceStock 3, simulateOrder, simulateEveryHours 24, simulatePerRun 20, costDriftKrw 500, unverifiableStreak 6, systemicFailCount 3, reconcileMarket), `prune`(stalePausedDays 14, replaceAdvantage 2, replaceMinGainKrw 10000, minAgeDays 30, windowDays 30, protectMonthlyProfitKrw 30000, maxReplacePerRun 2), `listing.zeroSaleDays`·`stopAfterLowerDays`, `schedule.monitorMinutes`

## 3-0-1. 아이템위너·상품명·Wing 직접 조작

**아이템위너("노출상태: 아이템위너 아님")**: 오너클랜 위탁 상품은 여러 판매자가 같은 이미지·상품명으로 올려 쿠팡이 한 상품으로 묶고 위너 1명만 노출한다(판매가+배송비 → 재고 → 출고소요기간 → 판매자점수). 쿠팡 OPEN API는 위너 여부·위너 가격을 제공하지 않아(개발자센터 FAQ, 확인 2026-10-14) 자동 대응은 하지 않는다.
- 위너가 아닌 상품은 판매가 거의 없으므로 **판매 부진 정리**가 자동으로 걸러낸다(14일 0건 → 하한가 1회 인하 → 10일 더 0건이면 판매종료)
- 빨리 정리하고 싶으면 **Wing에서 그 상품을 삭제**하면 된다(아래)

**Wing에서 상품 삭제 → 자동 반영(60분 내)**: 삭제된 상품은 실측(2026-10-14)상 옵션 조회가 오류 없이 **판매중지(onSale=false)**로 나오고 상품 조회만 "상품삭제"다. 그래서 쿠팡 판매상태 대조는 옵션이 모두 판매중지(또는 "유효한 옵션이 없습니다")이면 상품 조회로 "상품삭제"인지 확인해 **판매종료(쿠팡에서 삭제됨)**로 정리한다(이전 버전에서 "쿠팡에서 판매중지됨"으로 남은 상품도 다음 대조에서 정리). 관리 화면 상품 > **[쿠팡 삭제]** 탭에서만 보이고(전체·판매종료 목록에서 숨김), 같은 공급처 상품은 다시 등록하지 않는다. Wing에서 판매중지만 한 상품은 삭제로 보지 않는다. 심사 중 상품을 지워도 같다. 묶음 옵션 하나만 지운 경우는 정리하지 않는다. 상품 조회가 일시 오류면 다음 실행에서 다시 확인.

**Wing에서 가격을 직접 바꿔도 됨**: 쿠팡 실제 가격이 시스템과 다르게 두 번 연속(1시간 간격) 보이면 시스템 가격으로 반영(덮어쓰지 않음). 손실 가격이면 판매중지 후 동기화가 손실 없는 가격으로 올려 재개. 우리가 최근 3시간 안에 바꾼 가격은 반영 지연으로 보고 건너뜀. 끄기: `monitor.adoptMarketPrice=false`

**"상품명에서 옵션과 중복된 단어를 지워주세요"**: 쿠팡 상품명 정책(2025-10)은 옵션(색상·사이즈·수량)을 상품명이 아니라 구매옵션에 넣고, 같은 단어를 2회 넘게 반복하지 않게 한다. 고치지 않으면 노출 중지될 수 있다.
- 새로 올리는 상품: 노출상품명에서 구매옵션 값과 겹치는 단어를 자동으로 빼고(구매옵션엔 그대로), 같은 단어는 2번까지만
- 이전 버전으로 올린 상품: 승인된 상품명을 API로 바꾸면 쿠팡 재심사가 필요하고 그동안 판매 유지 여부가 공식 문서에 없어 자동으로 바꾸지 않는다. 관리 화면 > 상품 맨 위 **"상품명 정리 필요"**에 제안 이름이 나온다 → Wing > 상품관리 > 상품조회/수정에서 상품ID로 찾아 노출상품명을 제안 이름으로 바꾸기 → [수정함](여러 개는 [Wing에서 모두 수정함])
- 다른 상품과 잘못 묶여 다른 상품이 보이면: Wing > 판매자지원 > 온라인문의 > 상품관리 > 상품결합 및 분리요청

## 3-0-2. 공급처 옵션 → 쿠팡 구매옵션(색상·사이즈)

**여러 옵션 판매(`listing.multiVariant`, 기본 켜짐)**: 공급처 옵션이 여러 개면 재고 있는 옵션을 싼 순으로 최대 `listing.maxVariants`(10)개 골라 **쿠팡 구매옵션으로 모두 올린다**(예: 화이트 M·화이트 L·블랙 M…, 묶음 수량이 있으면 옵션×1·2·3개, 합계 최대 `listing.maxItems`(30)개 — 넘으면 큰 묶음부터 뺌).
- 옵션마다 **자기 원가로 하한가·판매가**(비싼 옵션은 더 비싸게, 손해 없음), 자기 재고로 최대 구매수량
- 고객이 고른 옵션 그대로 공급처에 발주(사람이 구매하는 도매꾹 주문은 주문 화면에 그 옵션 표시)
- 동기화: 옵션 하나만 품절·삭제·손실 가격이면 **그 옵션만 판매중지**, 재입고되면 자동 재개. 옵션이 모두 안 되면 상품 판매중지 → 하나라도 회복되면 재개(멈춘 옵션은 그대로). 옵션 원가가 바뀌면 그 옵션 가격만 조정
- 품절 옵션 주문이 들어오면 발주하지 않고 그 옵션만 판매중지(다른 옵션은 계속 판매)
- 구매옵션(색상·사이즈)이 다른 옵션과 겹치거나 값을 못 찾는 옵션은 빼고 등록(남은 옵션이 없으면 등록 안 함)
- 관리 화면 상품: `옵션 N개` 배지, 옵션별 판매가, 판매중지 옵션은 취소선(사유 표시)
- 이미 하나의 옵션으로 올라간 상품은 그대로 유지(바꾸려면 쿠팡 재심사가 필요해서 자동 변경 안 함). 끄면(`listing.multiVariant=false`) 아래 방식

**옵션 하나 판매(이전 방식·옵션 1개 상품)**: **옵션 하나를 정해(가장 싼 재고 옵션) 그 옵션으로 판매·발주**하고, 쿠팡 필수 구매옵션은 그 옵션에서 채운다.
- 오너클랜: 옵션 축(색상=그레이, 사이즈=높은 중형)을 그대로 사용
- 도매꾹/도매매: 주문옵션(selectOpt)을 해석(조합형 1·2축, 독립형 1축). 옵션별 추가금·재고·숨김 반영. 축 이름이 '옵션'처럼 일반적이면 값에서 찾음("심플바스켓 (3호 화이트)" → 사이즈 3호·색상 화이트, "제품선택/240" → 사이즈 240)
- 찾는 순서: 옵션 축 → 옵션 이름 → 상품명 → 상품정보고시
- **옵션마다 색상(사이즈)이 다른데 판매 옵션의 값을 못 찾으면 등록하지 않는다**(멀티·FREE 같은 자리채움 값으로 올리면 구매자가 무엇을 받는지 모름). 도매꾹 독립형 옵션이 여러 축이면 등록하지 않는다. 단일 상품이라 정보가 없을 때만 색상 '멀티'·사이즈 'FREE'
- 노출상품명에서는 옵션 단어를 뺀다(구매옵션에 있음). 사람이 구매하는 주문(도매꾹)은 주문 화면에 "옵션: 심플바스켓 (3호 화이트) — 이 옵션으로 구매"가 표시된다

**이전 버전으로 옵션 없이 올라간 상품**(쿠팡 옵션이 멀티/FREE): 공급처 옵션이 여러 개면 동기화가 **판매중지(옵션 미지정)**하고 알림 → 관리 화면 상품 > 해당 상품 > **[옵션 지정해 다시 등록]**: 옵션을 정해 정확한 구매옵션으로 새로 등록(쿠팡 심사), 이전 상품은 판매종료. 이전 쿠팡 상품은 Wing에서 삭제하면 자동 정리된다. 새 등록이 실패하면 이전 상품은 판매중지 상태로 남는다.

## 3-0-3. 상품 설정 자동 점검·수정(60분, `listings.repair`)

쿠팡에 올라간 상품(승인완료)을 쿠팡 상품 조회로 읽어 공급처 옵션 기준의 올바른 값과 비교하고, 틀리면 **쿠팡 상품 수정 API(승인필요)**로 고친다(조회한 JSON 전문에서 해당 값만 바꿔 전송 — 쿠팡 공식 방식, 옵션ID 유지).
- 점검 항목: 구매옵션(색상·사이즈·수량 등, 3-0-2 규칙) · 노출상품명의 옵션 단어 중복 · 옵션 여러 개인데 판매 옵션 미지정(기본 옵션 지정)
- 수정 요청 → **쿠팡 재심사** → 승인되면 다시 점검해 맞으면 완료. 판매중 상품은 심사 중에도 판매를 멈추지 않는다
- 시스템이 멈춘 **옵션 미지정** 상품은 고쳐서 승인되면 공급처가 판매 가능할 때 자동 재개(품절이면 공급처 사유로 바꿔 두고 재입고 시 동기화가 재개)
- **사람이 멈춘 상품은 자동으로 재개하지 않는다**(설정은 고침). 다시 팔려면 아래 [판매재개(검토 후)]

**[강제 판매중지]**(관리 화면 상품): 쿠팡 판매중지 + 동기화·설정 점검·쿠팡 대조 어느 것도 재개하지 않음. 진행 중인 자동 재개 예약도 취소. Wing에서 직접 다시 판매를 켜면 그 결정을 따른다.
**[판매재개(검토 후)]**: 바로 재개하지 않고 상태를 '재개 검토중'으로 두고 점검
1. 설정 점검(구매옵션·상품명·판매 옵션) — 정상이고 공급처 판매 가능 → 즉시 재개
2. 설정 오류 → 쿠팡에 수정 요청(판매중지 유지) → 승인되면 스케줄러가 다시 점검 → 맞으면 자동 재개
3. 고칠 수 없음·수정 실패·쿠팡 반려 → '재개 보류: 사유' + 알림(자동 재개 안 함). Wing에서 고친 뒤 다시 [판매재개]
4. 공급처 품절 → 공급처 사유로 두고 재입고 시 동기화가 재개
- 직접 연결한 상품(Wing 직접 등록)은 설정 점검 없이 공급처 확인만. 판매종료 상품도 같은 검토를 거쳐 재개, 쿠팡에서 삭제된 상품·안전장치 중지·긴급 정지 중엔 재개 불가
- (배포 전 예약분) 이전 버전에서 '수정 승인 후 재개'로 예약된 상품은 그대로 승인 후 재개된다. 원치 않으면 [강제 판매중지]
- 고칠 수 없으면(옵션 정보로 색상·사이즈를 정할 수 없음) 알림만, 실패·반려는 24시간 뒤 재시도(최대 3회) 후 Wing에서 직접 수정 안내
- 한 번에 최대 3개 수정 요청(재심사 몰림 방지), 직접 연결한 상품(Wing 직접 등록)은 건드리지 않음
- 관리 화면 상품 목록에 "설정 수정 심사중"/"설정 자동 수정 실패" 표시
- 쿠팡 상품 조회가 가끔 일시 오류(400 "오류가 발생하였습니다")를 주면 한 번 다시 시도하고, 그래도 실패하면 다음 실행에서 다시
- 설정: `repair`(enabled, perRun 3, retryHours 24, maxAttempts 3, reviewAlertHours 72), `schedule.repairMinutes`

## 3-0-4. 취소·반품·교환(클레임) — 5분마다(`orders.poll`)

쿠팡 반품/취소 요청(상태별 RU·UC·PR·CC + 즉시취소)과 교환 요청을 조회해 **접수 단위로 끝까지** 처리한다(주문 화면 "취소·반품·교환" 카드에 단계·처리 내역). 열린 접수는 끝날 때까지(최대 30일) 다시 조회하고, 목록에서 사라지면 단건 조회로 고객 철회를 확인한다.

| 상황(쿠팡 상태) | 자동 처리 | 사람이 할 일 |
|---|---|---|
| 결제완료에서 고객 취소(즉시취소, 쿠팡이 바로 환불) | 공급처 주문이 있으면 자동 취소 → 취소됨 | 없음 |
| 상품준비중에서 고객 취소(**출고중지요청**) — 오너클랜 | 오너클랜 주문 취소 → 취소 확인되면 쿠팡 **출고중지완료**(고객 환불) → 취소됨. 오너클랜이 "취소 요청"(준비중)이면 수락될 때까지 5분마다 확인, `orders.claimWaitHours`(24) 넘으면 알림 | 없음 |
| 위와 같은데 공급처가 이미 발송 | 쿠팡 **이미출고**(공급처 송장) → 고객이 반품(수취거부)으로 진행 → 반품 단계로 | 공급처 반품 접수(왕복 배송비 판매자 부담일 수 있음) |
| 상품준비중 취소 — 도매꾹·직접 구매 | 취소 요청 상태로 두고 알림 | 공급처에서 주문 취소 → 주문 화면 **[공급처 취소 완료]**(출고중지완료 자동) / 이미 보냈으면 **[이미 발송됨]**에 송장 |
| 구매 전 주문 취소 | 출고중지완료 → 취소됨 | (사람 구매 대기 중이었으면) 이미 샀는지 확인 |
| 부분 취소(2개 중 1개) | 자동 처리 안 함(확인 필요) | 공급처 수량 조정 후 Wing에서 처리 |
| 출고 후 반품 접수 | 반품 요청 상태 + 안내 1회(귀책·반품배송비) | 공급처에 반품 접수. 회수되면 쿠팡 빠른환불(10만원 미만)이 자동 환불, 아니면 입고 확인 후 **[반품 승인(환불)]** |
| 반품 완료 | 반품완료. 환불 정산이 들어오면 손익(원가 손실) 기록 | 없음 |
| 교환 접수 | 안내 1회 | 공급처 교환 접수 또는 **[공급처 재발송]**(자동 주문, 비용은 손익 차감) → 송장이 오면 알림 → Wing 교환 관리에 송장 입력 |
| 분실·파손 재발송 | **[공급처 재발송]** → 송장 회신 알림 | 고객에게 새 송장 안내 |
| 고객 철회 | 이전 상태로 복구(공급처 취소를 이미 요청했으면 확인 필요 알림) | (알림 시) 공급처 상태 확인 |

- 쿠팡 쪽 처리(출고중지완료·이미출고·반품 승인·판매자 취소)는 `LIVE_FULFILLMENT=true`일 때만 실제 호출(아니면 모의)
- 판매자 취소는 쿠팡 판매자 점수(주문이행)가 떨어진다고 쿠팡 문서에 명시 → 자동으로 하지 않고 버튼으로만
- 교환 송장 업로드 API는 요청 형식이 문서에 없어 자동화하지 않음(Wing에서 입력)
- 실측(2026-10-14): 교환 조회는 구간 7일 미만만 허용 → 6일씩 나눠 조회. 반품/취소 조회는 31일까지

**직접 테스트 주문(내 상품을 사서 취소)**: 결제 → 5분 안에 상품준비중·오너클랜 자동 발주(관리 화면 주문이 "구매완료"·공급처 주문번호 표시) → 쿠팡 앱에서 주문 취소 → 5분 안에 오너클랜 주문 취소 → 쿠팡 출고중지완료 → 주문 "취소됨" + 텔레그램 "고객 취소 자동 처리". 결제 직후(상품준비중 전)에 취소하면 쿠팡이 바로 취소해서 발주 자체가 일어나지 않는다.

## 3-0-5. 송장·배송(택배사 자동 판별) — 10분마다(`orders.fulfillment`)

공급처(오너클랜)가 송장을 등록하면 자동으로 쿠팡에 올린다. 택배사 표기가 공급처마다 달라서(이름·약칭·옛 이름·숫자 코드) 아래 순서로 쿠팡 코드를 정한다(`modules/orders/couriers.ts`).
1. 관리자가 정한 별칭(설정 `orders.courierAliases`) 2. 쿠팡 코드 그대로(CJGLS 등) 3. 쿠팡 공식 이름·흔한 별칭(대한통운·롯데글로벌로지스·현대택배·KG로지스·CU편의점택배·업체직송…) 4. 숫자 코드(04=CJ대한통운, 08=롯데…) 5. 이름에 포함된 가장 긴 별칭

| 상황 | 자동 처리 | 사람이 할 일 |
|---|---|---|
| 택배사를 못 맞춤 | 송장은 저장, "택배사 선택 필요" 알림(하루 1번) | 주문 화면 [택배사 선택 필요]에서 쿠팡 택배사 목록 중 고르기 → 등록 + **그 표기를 기억해 다음부터 자동** |
| 쿠팡이 송장 형식 거절(택배사별 자릿수) | 재시도, 3번째 실패 시 알림 1번. 공급처가 송장을 고치면 새 송장으로 자동 등록 | 공급처 주문의 택배사·송장 확인(택배사가 다르면 [송장 입력]에서 바로잡기) |
| 이미 다른 주문에 쓰인 송장 | 알림 | 공급처에 올바른 송장 요청 |
| 고객 취소 진행 중(출고중지요청) | 송장 등록 보류 → 취소 흐름(3-0-4)이 처리 | 없음 |
| 송장 등록 후 공급처가 송장을 고침 | 12시간 뒤부터 6시간마다 공급처 송장 재확인 → 쿠팡 **송장 수정**(배송지시·배송중 상태) | 없음 |
| 송장 등록 후 72시간(`orders.trackingStuckHours`) 넘게 배송 시작 안 됨 | 알림 1번(3일마다) | 공급처에 실제 발송 여부 확인(가짜·오입력 송장으로 고객이 취소하면 배송비 판매자 부담) |
| 업체직송(송장 없는 직접 배송) | 업체직송(DIRECT)으로 등록, 정체 알림 없음(쿠팡 배송조회 불가) | 없음 |

- 자동 발주가 되면 "새 주문 — 자동 발주 완료" 알림(원가·예상 이익)
- 직접 구매(도매꾹 등)는 공급처 주문 화면의 택배사·송장번호를 [송장 입력]에 넣으면 된다(택배사는 목록에서 선택)
- 반품 회수 방식이 **수기관리**면 쿠팡이 회수하지 않는다(실측 2026-10-14) → 반품 알림에 안내. 공급처 반품 접수 시 공급처 택배로 회수 요청, 회수 송장은 Wing 반품관리에 입력
- 공급처가 고객 취소 요청을 거절(취소요청 → 다시 준비중)하면 알림. 그대로 발송되면 자동으로 쿠팡 이미출고 처리

## 3-0-6. 네이버 스마트스토어(두 번째 판매채널)

쿠팡에서 **판매 중인 상품**을 스마트스토어에도 올려 노출 채널을 늘린다. 주문·발주·송장·취소·반품·교환·고객문의는 쿠팡과 같은 흐름으로 처리하고, 화면·알림에는 `스마트스토어` 표시가 붙는다. 키가 없거나 설정이 꺼져 있으면 아무것도 하지 않는다(쿠팡 운영에 영향 없음).

**켜는 순서**
1. 스마트스토어 판매자 가입·스토어 심사 완료, 스마트스토어센터 > 판매자 정보 > 주소록에 **출고지·반품/교환지** 등록(공급처 출고지가 아니라 반품 받을 주소)
2. 네이버쇼핑 노출: 스마트스토어센터 > 노출관리 > 노출 서비스 관리에서 **네이버쇼핑** 사용(안 하면 스토어에만 보임)
3. 커머스API센터(apicenter.commerce.naver.com) — **처음 스마트스토어를 만든 네이버 아이디**로 로그인 → 계정 생성 → 애플리케이션 등록(상품·주문·판매자 정보·고객문의 권한). 호출 IP를 묻는 항목이 있으면 맥 서버 공인 IP(맥에서 `curl -s https://api.ipify.org`)
4. `~/dropship/.env`에 `NAVER_COMMERCE_CLIENT_ID=…`, `NAVER_COMMERCE_CLIENT_SECRET=…` 두 줄 추가 → `bash ~/dropship/bin/restart.sh`
5. `bash ~/dropship/bin/check.sh` → "스마트스토어 커머스API: 인증·조회 성공(카테고리 …개, 출고지 1 · 반품지 1 …)" 확인
6. 관리 화면 설정 > **스마트스토어 판매 = true** (상품 화면 위에 "스마트스토어: 사용 중"이 보임)

**동작** (`naver.mirror`, 60분마다 최대 `naver.perRun`(5)개, 상한 `naver.maxListings`(200))
- 대상: 쿠팡 판매중(실등록) 상품 중 스마트스토어에 아직 없는 것, 오래 판매된 순
- 가격: 스마트스토어 수수료 `naver.feeRate`(7%)로 하한가·판매가를 다시 계산 → 쿠팡보다 같거나 쌈. 이후 원가 변동도 같은 기준으로 자동 조정
- 옵션: 쿠팡에서 판매 중인 옵션(공급처 옵션×묶음 수량)만. 스마트스토어 정책상 옵션가는 판매가의 ±50% 이내 → 넘는 큰 묶음은 뺌
- 카테고리: 오너클랜 카테고리 경로가 네이버쇼핑 분류와 같은 체계라 경로로 매칭(못 맞추면 건너뛰고 7일 뒤 재시도, `naver.categoryMap`으로 직접 지정 가능)
- 이미지·상세: 쿠팡 등록에 쓴 이미지·상세를 스마트스토어 이미지 서버에 올려 사용
- 배송: 무료배송(원가 포함), 제주·도서산간 추가 배송비 `naver.remoteAreaExtraFee`(5,000원), 반품 배송비 `coupang.returnCharge`, 교환 `naver.exchangeFee`
- KC 인증 상품은 인증정보 입력이 필요해 자동 등록하지 않음
- 등록 실패는 반려로 남기고 알림(7일 뒤 재시도)

**스마트스토어 전용 운영(자동)**
| 기능 | 동작 |
|---|---|
| 발송 지연 처리 | 발송 기한 당일까지 송장이 없으면 기한을 `orders.dispatchDelayDays`(2)일 미루고 사유(상품 준비 중) 등록 — 기한을 넘기면 판매 페널티. 주문당 최대 2번, 알림 |
| 배송지 변경 | 발주 확인 뒤 고객이 배송지를 바꾸면 새 주소 저장 + 공급처 주문도 바꾸라는 알림(공급처 1:1 문의) |
| 교환 재배송 | [공급처 재발송] 송장이 나오면 수거 완료 승인 → 교환 재배송 처리까지 자동(쿠팡은 Wing에서 직접) |
| 판매상태 대조(60분) | 스마트스토어센터에서 삭제 → 판매종료, 판매금지·판매중지 → 일시중지(자동 재개 안 함), 우리가 멈춘 상품이 판매중이면 다시 중지 |
| 문의 | 상품 문의(Q&A)와 주문 1:1 문의를 함께 수집·템플릿 자동 답변 |
| 감시 | 스마트스토어 주문 수집이 멈추면 급한 알림(야간에도) |
| 실수수료 학습 | 구매확정 정산 예정 금액으로 상품별 실제 수수료율 학습 → 가격 계산 |
| 송장 오류 | 비유효·기사용 송장(104122·104121)은 쿠팡과 같이 재시도·안내, 택배사 코드 오류(104119)는 택배사 확인 안내 |

**주문 처리**: 스마트스토어 '발주 확인'이 쿠팡 '상품준비중', '발송 처리'가 '송장 등록', '취소 요청 승인'이 '출고중지완료'에 해당한다. 고객이 고른 옵션의 판매자 관리코드로 공급처 옵션을 찾아 발주. 구매확정되면 정산 예정 금액으로 정산완료·이익 기록(쿠팡처럼 매출내역 대사 없음). 택배사 코드는 쿠팡 코드에서 변환(농협·CU·GS 편의점 등은 코드가 다름, 목록에 없으면 '기타택배').

## 3-0-7. 키워드 품질(공급처 확인)
검색광고 연관 키워드는 **오너클랜·도매꾹 검색 결과 상품명에 그 키워드가 들어간 상품이 3개 이상**일 때만 키워드 풀에 넣는다(`discovery.supplyCheck`). 카드·바우처류('농협법인카드' 등)는 제외어로 거른다. 공급 없음은 30일 기억하고, 예전 규칙으로 들어온 미사용 키워드도 발굴할 때마다 조금씩 재확인해 정리한다(1회 검색 200회·2분 한도, 새 키워드 3/4·재확인 1/4, 못 본 키워드는 다음 발굴로). 키워드 전부를 빠른 도매꾹으로 먼저 확인(실측 0.2~0.4초)하고 부족한 것만 남은 시간에 오너클랜(4~70초) — 오너클랜 API를 오래 붙잡지 않아 발주에 영향이 없게. 실측(운영 DB 복사본): 발굴 72초, 새 키워드 약 50개 공급처 확인.

## 3-1. 자동 안전장치(구매자 보호)
감시 작업(10분마다)이 문제를 찾으면 텔레그램 **⚠️ 문제 감지**(해결 방법 포함) → **3시간** 안에 해결되지 않으면 **🛑 자동 판매 중지**.
- 판매 중지 = 쿠팡 판매 상품 전부 판매중지(새 주문 차단) + 자동 등록 중지 + 자동 재개 금지
- **이미 결제된 주문은 계속 처리**(멈추면 그 구매자가 피해). 주문별 안전장치(품절·역마진·한도)는 그대로
- 감지 항목: 6시간 넘게 처리 안 된 주문, 출고 기한 지난 송장 없는 주문, 주문 수집 1시간 이상 실패, 주문·송장·재고·주문 가능 점검 작업 3회 연속 실패
- 즉시 중지: 6시간 안에 예외 주문(품절·역마진·발주 오류·확인 필요) 3건 이상(구조적 오류)
- 알림만(중지 안 함): 12시간 넘은 미답변 고객 문의
- 해결 안 된 문제는 3시간마다 재알림, 해결되면 "✅ 문제 해결됨"
- 재개: 관리 화면 **[문제 해결 — 판매 재개]** 또는 `bash ~/dropship/bin/resume-sales.sh`(상태만: `... status`). 남은 문제는 유예를 새로 받고, 계속 남으면 다시 중지
- 관리 화면 **[긴급 정지]**(수동)는 자동 처리 전부 중단 + 쿠팡 판매도 중지. 해제하면 판매도 재개
- 소액 손실(2,000원 이내) 주문은 구매자 보호를 위해 그대로 발송, 상품만 중지 후 가격 재조정
- 텔레그램이 1시간 동안 계속 실패하면 healthchecks 에 실패 신호 → 이메일로 알림
- 설정: `safety.autoHalt`(끄기), `graceHours`, `stuckOrderHours`, `burstCount` 등

## 쿠팡 등록 사전 점검(`bash ~/dropship/bin/verify-listing.sh`)
- 상위 후보 1개를 쿠팡에 **임시저장**(심사 요청 안 함, 고객에게 안 보임)으로 보내 쿠팡이 받아주는지 확인하고 바로 삭제합니다.
- 실측으로 확인한 쿠팡 규칙(2026-10-14):
  - 구매옵션 값에 "상세페이지 참조" 같은 의미 없는 값은 거부됨 → 색상은 "멀티", 사이즈는 "FREE"로 채움
